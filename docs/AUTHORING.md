# AUTHORING — emulator-labs content contract

This is the binding contract for authoring chapters. Read it fully before
writing any template. `templates/ch00_pilot/` is the living reference example.

## Repository layout

```
emulator-labs/
├── templates/chNN_slug/          # SOURCE OF TRUTH (full implementations + stubs)
│   ├── LECTURE.md                # chapter lecture notes
│   ├── README.md                 # overview, gate checklist, verification notes
│   ├── NN_exercise_name/         # self-contained exercise (own CMakeLists)
│   │   ├── CMakeLists.txt
│   │   ├── *.cpp/*.hpp           # annotated sources (@LABS blocks)
│   │   └── SPEC.md               # optional per-exercise specification
│   ├── 90_debug/                 # debugging exercise (bugged stubs, correct solution)
│   ├── 91_challenge/             # challenge docs + fixtures (+ code if needed)
│   └── 99_coding_test/           # unseen-spec coding test entry + spec
├── tests/public/chNN_slug/       # fixtures, golden traces/frames used publicly
├── tests/hidden/chNN_slug/       # manifest.json + fixtures for make grade
├── docs/chapters/chNN_slug*.md   # extra chapter essays (optional)
└── tools/labs/                   # infrastructure (do not modify per-chapter)
```

## Skeleton marker grammar

Inside any text file:

```
//@LABS-BEGIN <seq>          comment prefix may be // # ; ! * or "
//@LABS-SOLUTION
...reference implementation...
//@LABS-STUB
...compilable stub containing TODO(<seq>)...
//@LABS-END
```

Rules:

1. `<seq>` is an integer unique per FILE, ordered by task progression
   (1, 2, 3...). Blocks emit STUB by default; `--todo N` emits SOLUTION for
   `seq <= N`; `--mode solution` emits all SOLUTIONs.
2. Text outside blocks is copied verbatim **in position** (namespace closers,
   `#endif`, class braces stay put). Never span a block across a brace you
   don't close inside it.
3. **Stubs MUST compile and link** (return a wrong-but-typed value, leave a
   TODO comment). A generated skeleton must BUILD and its tests run RED.
   Never emit bare declarations for functions the tests call.
4. Every stub body contains the literal token `TODO(<seq>)`.
5. One conceptual task per block. 3–8 blocks per exercise is typical.
6. For the debugging exercise (90_debug): the STUB side carries the seeded
   BUG, the SOLUTION side is the corrected code. Document symptoms in
   `DEBUGGING.md`; students produce a `bug-report.md`
   (bug / root cause / first divergence / fix / regression test).

## CMake conventions

Each exercise dir owns a `CMakeLists.txt`. All targets/tests are namespaced
to avoid collisions:

```cmake
add_executable(ch03_02_fetch_tests main.cpp decoder.cpp)
target_link_libraries(ch03_02_fetch_tests PRIVATE labstest)
add_test(NAME ch03_02_fetch COMMAND ch03_02_fetch_tests)

# Headless runner CLI (mandatory shape, curriculum §52):
add_executable(ch03_02_fetch_runner runner_main.cpp ...)
add_test(NAME ch03_02_fetch_runner_help COMMAND ch03_02_fetch_runner --help)
```

Runner CLI (every system implements the same flags):

```
--rom PATH --headless --cycles N --frames N --trace FILE --hash-frame FILE
--input-file FILE        # scripted keypad/controller input, one frame per line
```

Trace line format (consumed by compare_trace.py):
`pc=<hex> op=<hex> [reg=val ...] cyc=<n>` — whitespace-separated key=value,
lowercase keys. Golden traces live under `tests/public/<chapter>/traces/`.

## Test framework

`third_party/labstest/labstest.hpp`: `TEST(suite,name)`,
`EXPECT_TRUE/FALSE/EQ/NE`, `#define LABSTEST_MAIN` in exactly one TU,
link `labstest`. Deterministic only — no time, no RNG without fixed seed,
no host paths in assertions.

## Golden data policy

Golden hashes/traces are GENERATED BY THE REFERENCE SOLUTION (run twice,
must be identical) and committed under `tests/public|hidden/<chapter>/`.
Document the generating command in a `provenance.md` next to the goldens.
Never hand-invent a hash.

## ROM & fixture policy

Commercial ROM images NEVER enter the repo. Fixtures are programs we
assemble ourselves (byte arrays committed with a `.asm.txt` disassembly +
provenance note) or student-supplied dumps. External suites (Timendus
CHIP-8, Mooneye, nestest, mGBA suite, ps1-tests) are optional: reference
them by URL, gate them with `"requires_rom"` in hidden manifests so grading
skips gracefully when absent.

## Hidden manifest schema (tests/hidden/chNN_slug/manifest.json)

```json
{"description": "...",
 "cases": [
   {"name": "unique_case",
    "binary": "build/skels/chNN_slug/NN_ex/target",     // or solutions path
    "args": ["--rom", "tests/hidden/chNN_slug/roms/x.bin", "--cycles", "1000"],
    "expect_exit": 0},
   {"name": "frame_golden",
    "binary": "...", "args": ["--rom","{{tmp}}/r.bin","--frames","10",
                              "--hash-frame","{{tmp}}/f.rgba"],
    "expect_file_hash": {"file": "{{tmp}}/f.rgba", "fnv64": "XXXXXXXXXXXXXXXX"}},
   {"name": "hardware_suite_optional",
    "binary": "...", "args": [],
    "requires_rom": "roms/gb/mooneye/timer.bin", "optional": true}
 ]}
```

Note `binary` paths assume `make build` output layout
(`build/skels/...`). Grade runs from repo root; use `{{tmp}}` scratch dirs.

## Gate mapping

Chapter gate (curriculum §4) components map to artifacts:

| Component   | Artifact |
|---|---|
| exercises   | all `NN_*` dirs: skel RED -> student GREEN |
| starter     | chapter generates, builds, runs (`make skels && make test`) |
| debug       | `90_debug`: fix seeded bugs + `bug-report.md` |
| challenge   | `91_challenge`: acceptance criteria met |
| coding_test | `tests/hidden/chNN_slug/manifest.json` fully passing |

## Verification bar

After authoring a chapter you MUST verify from repo root:

```bash
python3 tools/labs/generate.py --force --targets chNN_slug
cmake -S . -B build && cmake --build build -j && \
  ctest --test-dir build --output-on-failure          # skeletons RED (or skipped)
python3 tools/labs/generate.py --mode solution --force --targets chNN_slug
cmake -S . -B build-solutions -DLABS_BUILD_SOLUTIONS=On && \
  cmake --build build-solutions -j && \
  ctest --test-dir build-solutions --output-on-failure  # solutions ALL GREEN
python3 tools/labs/grade.py --repo . chNN_slug          # hidden manifest passes
```

Solution-tree GREEN is non-negotiable for every shipped exercise. If a case
genuinely needs student-supplied hardware dumps, mark it `requires_rom` +
`optional` — never fake a pass.

## Style

C++20, no external dependencies beyond labstest. Clear names over comments;
comments explain WHY (hardware behavior), not WHAT. Every chapter README ends
with a "Verification" section recording exactly what was run and what passed.

## Integration conventions (learned the hard way — binding)

1. **Hidden-manifest `binary` paths use `build/skels/...`** (the standard
   `make build` layout). Grade turns green when the student solves the
   chapter; that is the intended semantics. Never point at
   `build/solutions/`.
2. **Stubs must terminate.** Any stubbed `step()`-like function that feeds a
   `run()`/`while` loop MUST charge nonzero cycles and advance state so a
   generated skeleton hangs never. RED assertions, not timeouts.
3. **labstest `EXPECT_EQ/NE` decay-copy both operands** and evaluate them
   exactly once. `*f().member` style expressions are safe.
4. **Bugged-stub dirs (`90_debug`, `99_coding_test`) are exempt** from the
   TODO-marker warning; their stub side intentionally ships bugs, not TODOs.
5. `verify_chapter.sh` wipes its prefix per invocation — pass ALL targets of
   a multi-chapter batch in one call.
6. Descriptive gate-dir names (`91_boot` instead of `91_challenge`) are
   acceptable ONLY when the chapter README maps them explicitly to the
   gate component. The audit treats the README as source of truth.

## Language policy (intentional)

```
course implementation   → ISO C++20
strict-C track cores    → strict ISO C17 (docs/CURRICULUM-foundations-c17.md)
grading tooling         → C++20 / Python
platform frontend       → anything, OUTSIDE the core
```

Root CMake declares both standards; never let a core drift languages
mid-chapter. Platform headers stay out of every core (`make lint-portable`).

## Bus transactions are first-class test data

Register-level assertions can pass while memory accesses run in the wrong
order. Whenever a chapter's CPU/device touches MMIO, DMA, or serial
peripherals, record and pin the transaction sequence too:

```cpp
struct BusTxn {
    uint64_t cycle;
    uint32_t address;
    uint32_t data;
    uint8_t  width;   // 1/2/4 bytes
    uint8_t  write;   // 1 = write, 0 = read
};
```

A step result may then be verified as: architectural state + cycle count +
exact bus transaction sequence. Existing exemplars: ch19 `RecordingBus`,
ch24 DMA accounting.

## Trace format versioning

Every golden trace file begins with a header line `EMU_TRACE_V1`. Comparers
reject unknown versions instead of mis-parsing future formats.

## Golden metadata schema

Next to every generated fixture set, provenance.md (or a sidecar .json)
records:

```json
{
  "fixture": "adc_case_42.bin",
  "generated_by": "reference_cpu",
  "validated_against": "external_suite_or_manual_proof",
  "generator_seed": 1234,
  "format": "EMU_TRACE_V1"
}
```

Running the reference twice proves DETERMINISM only. Correctness comes from
validating against an independent oracle — public test suite, PSX-SPX /
NESdev-defined behavior, or a hand-proved vector — before minting goldens.

## Assertions vs hardware quirks

Assert programmer invariants (`assert(idx < TABLE_SIZE)`) freely. Never use
assertions to declare real hardware behavior impossible: if the silicon does
it, the emulator must do it. Weird-but-legal gets implemented and tested,
not asserted away.

## Unknown MMIO diagnostics

Never silently `return 0` for unimplemented space. Log deterministically:

```
UNHANDLED READ8 addr=0x4018 pc=0xC123 cyc=44102
```

so failures arrive with clues attached.

## Terminology

Committed grading cases are called **unseen tests** (they exercise
specifications learners have not practiced). The directory
`tests/hidden/` is historical naming and stays for path stability.
