# Chapter 47 Lecture — the PlayStation SPU

The Sound Processing Unit is a self-contained 24-voice sample player with
its own 512 KiB RAM, its own clock domain (44100 Hz), and its own interrupt
line. It sits on the bus as a register window at `1F801C00..1F801DFF` plus
four DMA channels (we use the manual-transfer mode here).

## Voices

Each of the 24 voices owns a 16-byte register slice:

| Offset | Register    | Meaning                                   |
|--------|-------------|-------------------------------------------|
| +0x00  | VOL_LEFT    | output volume, left                       |
| +0x02  | VOL_RIGHT   | output volume, right                      |
| +0x04  | PITCH       | sample rate, 0x1000 == 44100 Hz           |
| +0x06  | START_ADDR  | SPU RAM address >> 3                      |
| +0x08  | ADSR1       | attack/decay/sustain-level                |
| +0x0A  | ADSR2       | sustain/release                           |

Voices start together via the KEY_ON bitmask (`1F801D88..90`) and stop via
KEY_OFF (`1F801D94..9C`). Bit *v* of the mask addresses voice *v*.

## ADPCM

SPU samples are stored as 16-byte blocks: 28 compressed samples per block,
4 bits each. Byte 0 packs `shift | filter<<4`, byte 1 carries flags:

* bit 0 — loop end: last block of the sound or of the loop body;
* bit 1 — mute: silence the voice after this block;
* bit 2 — loop start: remember this address for loop_end jumps.

Nibbles are **low nibble first**. Each nibble is sign-extended, shifted
left by the shift value, then corrected by a two-tap predictor:

```text
s = raw + ((hist1*c1 + hist2*c2) >> 6)
```

The published coefficient table is exact — get one entry wrong and every
golden hash in this chapter fails:

| filter | c1  | c2  |
|--------|-----|-----|
| 0      | 0   | 0   |
| 1      | 60  | 0   |
| 2      | 115 | -52 |
| 3      | 98  | -55 |
| 4      | 122 | -60 |

Filters 5–7 are reserved; we clamp to 4 like most emulators do. The history
carries across blocks until key_on or reset clears it.

## Pitch

The mixer runs at exactly 44100 Hz. The pitch register is a fixed-point
multiple: `rate = pitch / 4096`. Playback therefore consumes
`pitch/4096` stream samples per output sample — a fractional position that
needs an accumulator. When less than one whole new sample arrives you must
interpolate. Real hardware uses a 4-point gaussian FIR; this course uses
linear interpolation between the two newest samples and documents that
simplification openly. The interpolation function is a single seam: swap in
a gaussian table later without touching any caller.

## Volume and sweep

Volume registers act as multipliers on the decoded sample. The real
hardware has saturating semantics and optional sweep (automatic volume
ramps); our model uses a plain linear scale with unity at `0x4000`
(`out = sample * vol >> 14`) and leaves sweep out of scope — the register
map accepts the writes so games do not notice the difference at this
fidelity tier.

## ADSR

Every voice carries a four-phase envelope: Attack → Decay → Sustain →
Release. Rates are packed into ADSR1/ADSR2 bitfields (7-bit attack and
sustain rates, 4-bit decay, 5-bit release). The published timing tables map
a rate to "one step of magnitude 7..4 every N samples", where the period
halves roughly every four rate codes. We implement that shape directly:

```text
period = 1 << max(0, 11 - (rate >> 2))
step   = 7 - (rate & 3)
```

Linear phases add/subtract `step`; exponential phases scale by
`max(1, (level*step) >> 6)`. Decay is always exponential on real hardware.
This exponential approximation follows the published doubling-time shape
without reproducing hardware cycle-exactness — a documented fidelity
choice, tested against golden values generated by the reference solution.

## Noise and reverb

Noise generator (rate-controlled LFSR driving voices whose ADPCM flag says
"noise") and reverb (a convolution work-area in SPU RAM behind ~32
registers) are real features we deliberately skip. The reverb registers are
**accepted and stored but bypassed**: audio never enters the effect. This
keeps games running while keeping the scope honest — see the exercise
comments before claiming otherwise in your own emulator write-up.

## SPU RAM and DMA

512 KiB of dedicated sound RAM, written either by CPU transfers through the
transfer-address register or by DMA channel 4. Our model exposes
`dma_write(addr, bytes)` with end-of-RAM clamping.

## CD audio input

The CD decoder's stereo output feeds the SPU through the CD volume
registers and is mixed into every frame. The exercise stub lets tests inject
a fixed CD input pair; wiring the real CD-ROM sector audio in is chapter 49
material.

## IRQ9

An address comparator watches SPU RAM: when a voice's decode address or a
DMA transfer lands exactly on the configured match address (and control bit
6 enables it), the IRQ flag latches and interrupt line 9 asserts toward the
INTC. Games use it to chain streaming audio buffers — chapter 49's
scheduler will make the delivery order matter.

## The reference architecture

```text
key_on event ──► voice state ──► ADPCM decode ◄── SPU RAM ◄── DMA / CPU
                     │               │
                  pitch stepper     flags (loop/mute/end)
                     │
                 interpolation ──► envelope gain ──► voice volume
                                                        │
              CD input ──► CD volume ──► mix ──► main volume ──► output
```

Everything processes in guest sample time: rendering N frames always takes
exactly `N * 768` CPU cycles because 33.8688 MHz / 44100 Hz = 768.
